# HAR file: read the requests a page made instead of opening it again

Every browser try saves three files: a HAR file with every request and response (logins, cookies and keys are masked before it is saved), the page's HTML, and a list of every request the page made. Look in these files before you open another window. Read only the parts you need. Some response bodies may be missing or cut short, so do not assume every answer is there.

The try's result lists the page's requests under `$capture`: for each request its kind, address, status, time and size. A row with `count` stands for several requests: either repeats of one address, or every request of one kind of page file (stylesheet, script, font, image, media, check, or tracking for bot-defence and analytics scripts). To read the files, pass "$recorded:har", "$recorded:page" or "$recorded:calls" as an input of a code try, which opens no window, and read it with `read_input`. `read_input` on the calls file or the HAR file takes the filters `url`, `method`, `status`, `kind` and `ids`, for example `read_input("calls", ids=[3, 7])`. Add `#2` to the name to read window 2's files.

Look first at the requests that carry the task's data: the ones that return JSON (kind xhr or fetch), and the page's own HTML when the site builds the page on its server. Skip stylesheets, scripts, images and tracking unless the task needs them. Use each request's time to see which action caused it. A request that repeats every few seconds does not show the page has finished loading.

From the request you need, write down its address, its parameters, and what a successful answer looks like. A login header or cookie in the HAR file is masked, and you cannot reuse it as a credential. Steps cannot read the browser's cookie files. Never copy a browser cookie into a step's output, and never read the app's saved session files.

A request that only works because the browser is signed in stays inside the browser step, called from the page as described in "browser/api-routes". Moving it into a connector step needs its own credential the user has given, the hosts declared on the step, and a try that shows it works. Seeing the address in a HAR file is not enough.

An HTTP 403 or a captcha is something to look into. It is never a reason to disguise the browser or to switch to a route with more access on your own. Stop when the site refuses permission or says you are sending too many requests. Changing to another route needs the user's agreement and its approvals, as any change does. The user's signed-in session is only for the task the user asked for: never use it to explore the account or call other addresses.
