# A step that cannot be tried for real now

This covers two situations, with one rule: the step is built complete, its first real run is its first real test, and you say so plainly rather than working round it.

When the user says no to the test send, that is their decision, and it does not stop the build. Keep the step complete in the plan: its code, and the test you wrote for it (how it builds the data it sends, and what a successful answer from the service looks like), so the build includes it. Only the real send is left out: the first real run makes it, after the user approves it on the run's approval popup, and the build records that the step was built without a recorded send. Never redesign the plan round it, never question the user's choice, and never ask again later in the same build.

When what starts the step cannot be made to happen now (for example the signed-out path while the user is signed in, or the error path while the service works), the step stays untried by choice. Say so plainly in one line, keep the code and the test you wrote on the step, and the first real run tries it. Never cause the condition on purpose by breaking something, and never keep trying to make it happen.

Offer a real test only when it is safe and can actually be done, and do not ask again after the user says no. Leaving the real send out does not excuse anything else: missing code, wrong inputs or outputs, unsaved settings or other things the build reports still have to be fixed. Record that the step was left untried, or that the user said no, in the way the tools allow, and go by what the tool's result says: never describe a refusal as success. If data from an earlier test send needs deleting, offer that as a separate change the user approves. A real run still asks before it sends, as always.
